# 1. 한 줄

이찌방쿠지 표준 추첨 메커닉(박스 비복원 + Last One + Double Chance)을 베이스 엔진으로 구축하고, `一番くじ ドラゴンボール THE CHRONICLE OF GOKU` 라인업으로 첫 시뮬레이터 화면을 출시한다.

# 2. 스코프 (in scope)

## 2.1. 추첨 엔진 (core)

2.1.1. 박스 단위 비복원 추첨 (PRNG, 결정론 시드 입력 가능).
2.1.2. 박스 매수 / 등급 / 등급별 매수 정의 데이터 입력.
2.1.3. Last One 보너스 트리거 (박스 마지막 1매 추첨 시 보너스 동시 지급).
2.1.4. Double Chance 응모 (추첨 1회마다 응모권 누적, 박스 종료 또는 사용자 시점에 응모 풀에서 별도 추첨).

## 2.2. 라인업 데이터

2.2.1. `一番くじ ドラゴンボール THE CHRONICLE OF GOKU` 1종.
2.2.2. 박스 80매 (`research/lineups.json` `box_size_estimated:true`).
2.2.3. 등급 A~J + Last One.
2.2.4. 등급별 매수 SSOT (`research/lineups.json` 추정 분포 그대로 차용, `count_estimated:true` 보존).
2.2.5. Double Chance 상품 (大猿悟空 SOFVICS, winners_total: 50, ラストワン賞과 동일 상품).

## 2.3. 화면 (render)

2.3.1. 박스 카드 (현재 박스 ID / 잔여 매수 / 가격 / 등급 분포 요약).
2.3.2. 추첨 버튼 + 결과 모달 (등급 / 상품명 / 사이즈 / Last One 보너스 동시 지급 시 합쳐 표시).
2.3.3. 등급별 잔여 표시 (くじ券回収貼付け表 형태).
2.3.4. 추첨 이력 (사용자 누적 추첨 결과).
2.3.5. Double Chance 응모 풀 + 추첨 버튼 + 결과.

## 2.4. 데이터 영속

2.4.1. localStorage prefix `kuji_`.
2.4.2. 박스 잔여 / 추첨 이력 / Double Chance 응모권 보관.
2.4.3. 시드(seed) 보관 (재현 가능).

## 2.5. 테스트

2.5.1. 추첨 엔진 결정론 (같은 시드 → 같은 추첨 순서).
2.5.2. 박스 80매 비복원 (중복 0).
2.5.3. Last One 트리거 (마지막 1매 시점에만 활성).
2.5.4. 등급별 매수 정합 (추첨 결과 합 = SSOT 정의).
2.5.5. Double Chance 응모 풀 누적 정합.

# 4. 성공 기준 (acceptance criteria)

4.1. 사용자가 모바일 웹에서 박스를 열고 80매를 모두 뽑을 수 있다.
4.2. 80매 뽑는 동안 등급별 매수가 SSOT 정의와 정합한다.
4.3. 마지막 1매 추첨 시 Last One 보너스(大猿悟空 SOFVICS)가 자동 지급된다.
4.4. 추첨 1회마다 Double Chance 응모권이 누적되고, 응모 풀 / 추첨 결과가 표시된다.
4.5. 같은 시드로 박스를 다시 열면 추첨 순서가 결정론적으로 동일하다.
4.6. 모든 매직 넘버가 `src/data/numbers.js`에 정의되어 있고 코드에 인라인 매직 값이 없다.
4.7. core/ 모듈에 DOM/window/document import가 0개다.
4.8. 핵심 모듈(추첨 / 박스 / Last One / Double Chance)의 단위 테스트가 100% pass다.
4.9. 추정값(박스 80매 / 등급별 매수)은 UI에 "추정" 배지로 표시되어 사용자가 신뢰도를 인지한다.

# 8. 리스크

8.1. 박스 80매 추정값. `lineups.json`에서 `box_size_estimated:true` / 등급별 매수 `count_estimated:true`. 실제 박스 사진 / 一番くじ 공식 매수표가 발견되면 정정 필요. 시뮬레이터에는 "추정" 배지로 노출하여 정합성 부담을 사용자에게 위임.
8.2. Double Chance 추첨 시점 / 당첨 풀 운영이 매장 / 온라인에서 다름. 시뮬레이터에서는 "추첨 후 Double Chance 응모권 누적, 박스 종료 시 또는 사용자 명시 시점에 응모 풀에서 추첨" 단순화 가정.
8.3. 표준 메커닉 베이스가 잘 짜이지 않으면 M2~M5 확장 시 재작성 부담 증가. 단계 4 구현 플랜에서 시스템별 어댑터 인터페이스를 명시 필요.
8.4. 한 박스 다 뽑은 후 사용자 동선이 약함. "다음 박스 열기 / 시드 변경 / 통계 보기" 동선이 7 QA에서 발견될 가능성. P2로 둠.
